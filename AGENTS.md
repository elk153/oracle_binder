## App at a glance

- React 19 + Vite SPA that finds Magic: The Gathering cards through the public Scryfall API (`https://api.scryfall.com`). Routing uses `react-router` 8 (`createBrowserRouter`).
- The app has one V2 layout. Home shows a daily seven-card set as a fanned "Hand of the day" (D-073); search results support local color, rarity, type and sorting controls; card details show artwork, rules/legalities and printings with current EUR / foil EUR prices. Favorites are saved to Supabase and displayed in a paginated favorites page. The Binder tracks per-copy metadata, folders, loose copies and disposed-copy history. Decks supports managing Binder, proxy and virtual card entries, with All cards and deck-list views. Advanced search is implemented for both sources: a form (`AdvancedSearchForm`) writes `s_` URL parameters, Scryfall results use `toScryfallQuery`, and collection results use the local `matchesAdvancedFilters` (D-050 to D-055).
- The V2 layout has a dark/light theme control. Theme state is shared through React context, defaults to dark on each page load, and is not persisted.
- No custom application backend or user database. Supabase Auth provides sign-in and sign-up through GitHub and Discord OAuth only (D-067 to D-070); there is no email/password sign-in, and the app sends no email. Account data is managed by Supabase. TanStack Query caches remote data in memory and persists some of it in browser `localStorage`.
- Binder copies track acquisition/location details and disposal status. Basic deck and card-entry management is implemented; full deck-building tools such as format validation, collection valuation and price history, sales and balance remain **goals, not features**. Never imply they exist.

## Routes

Defined in `src/app/router.tsx`. `/` redirects to `/v2/home`. Home and Search (`CardBrowserPage`) are in the main chunk; Login, auth callback, Scan, Favorites, Binder and Decks load on demand through React Router's `lazy` with the loaders in `src/app/lazyPages.ts` (D-071). Both top-level routes use `RouteErrorPage` as `errorElement`: a code chunk that fails to load after a deploy shows a "new version" prompt with Reload, an unknown address shows "Page not found", and other errors show "Something went wrong" (details in development only).

## V2 flow

- `index.html` loads `/src/main.tsx`; at build and dev time the `inlineSplashLogo` plugin in `vite.config.ts` replaces the splash `<img>`'s `/favicon.svg` with a `data:` URL of `public/favicon.svg` (D-071), so the first paint needs no extra request; `main.tsx` imports `src/styles/tokens.css` and mounts `AppProviders` in `StrictMode`.
- `AppProviders.tsx` nests `ThemeProvider` > `PersistenceProvider` > `QueryDevToolsProvider` (receives `queryClient` as a prop) > `RouterProvider`.
- `src/app/App.tsx` renders the V2 `NavBar` and child routes through `<Outlet />`. Background work waits for the first screen (D-071): `useBackgroundReady` (`src/hooks/`) turns true once the persisted cache is restored, no query is fetching, and two checks 300 ms apart (each after an idle moment: `requestIdleCallback`, 300 ms timer fallback) find no on-screen image in `<main>` still loading (15 s limit); only then `App` mounts `BackgroundWork`, which prefetches Scryfall card symbols, set metadata and the card-name catalog and preloads the Binder, Decks and Favorites page code one after another (`preloadLikelyPages`). The card-name catalog refreshes at the next local 04:00 boundary. The Home route renders `CardBrowserPage` in mulligan mode, which does not request the card-name catalog (no search box there).
- `src/features/card-browser/CardBrowserPage.tsx` handles `/v2/home`, `/v2/search`, and `/v2/search/random`. Home chooses a stable set per UTC day from released, non-digital, booster-focused Scryfall set types, requests unique cards in random order, and displays up to seven cards from the first result page. In mulligan mode (Home and `/v2/search/random`) the page shows a "Hand of the day" heading with the set name and renders the cards as an `<ol class="hand">` of `CardTile`s without the filter bar (D-073): each item gets a `--hand-offset` custom property (distance from the middle card) that `CardBrowserPage.css` turns into a fan angle and arc; hover or `:focus-within` brings a card to the front and lifts it (no lift under reduced motion), and at 540 px and below the hand becomes a sideways-scrolling row. The set-type allowlist lives in `mulliganSets.ts`; Scryfall does not supply a direct booster-eligibility flag.
- `src/features/search/` contains the search-page source, simple/advanced mode controls, typed `AdvancedSearchFilters` URL parsers, and the Scryfall query builder. `source` remains the collection selector and `s_mode` selects the mode (default `simple`); simple search submits `q` from a labeled native-datalist name autocomplete, while advanced search uses `AdvancedSearchForm`, which keeps a local draft of the filters and writes the `s_` parameters to the URL (nuqs) when Search is pressed; the model and Scryfall query integration are described in D-050, D-051 and D-054, and a set filter (`s_set`, stored as a set code) is included, as is a language filter (`s_lang`, a Scryfall language code such as `fr`, built as `lang:fr`; D-074). Advanced parameters use the `s_` prefix. Suggestions use the Scryfall card-name catalog or hydrated collection names, depending on source; the reusable component limits case-insensitive substring matches to 20 after four characters and can also consume set names for advanced search. Card filtering and sorting remain in `src/features/card-filters/` and are rendered by card browsers; collection search additionally filters by Binder/deck place and owned/proxy/virtual/favorite kind, with place sorting.
- Simple name search and advanced Scryfall search use the paginated `useScryfallCardPages` hook with an explicit load-more button; advanced filters build Scryfall syntax from `s_`-prefixed URL state, and price bounds request unique prints. Filters and sorting apply to cards loaded so far, plus matching favorited printings not on the current simple-name search pages. The `source=collection` scope searches deduplicated favorites, owned Binder copies, and all deck entries; disposed Binder copies are excluded, and `q` matches card names case-insensitively. With `source=collection` and `s_mode=advanced`, `matchesAdvancedFilters` (`src/features/search/`) applies the same filters locally to the hydrated collection cards (`q` is ignored); it mirrors `toScryfallQuery` and is described in D-052 and D-055. The daily set uses `useScryfallCardsSearch` for a single page of up to seven cards. `?card=<id>` opens the details overlay without replacing the current search URL.
- The protected `/v2/favorites` page uses `useFavoriteCards` to page Supabase favorites newest-first with a composite cursor, hydrates each batch of up to 75 card IDs through Scryfall's collection endpoint, preserves the Supabase ordering, and skips IDs no longer present in Scryfall. It reuses `CardFilters` to filter and sort currently loaded favorites.
- `features/favorites/useFavoriteCardAction.ts` shares favorite IDs and the toggle mutation across CardBrowser, Binder, and Decks; the calling page reports results through the app-wide notification stack (`useNotify`, D-080). The toggle is optimistic (D-071): `useToggleFavorite`'s `onMutate` writes the new ID list into the `["favorites", userId]` cache at once (skipped while the list is not loaded yet), `onError` restores the snapshot, and `onSettled` refetches in the background without keeping the mutation pending; hearts stay disabled only during the one Supabase write.
- `src/features/binder/` contains the paged `useBinderCopies` query, copy add/edit/dispose/history controls, and `/v2/binder`. A physical copy has one storage location: a Binder folder, a deck, or Loose. Deck assignment is represented by a `kind='binder'` deck entry and clears `binder_cards.binder_id`; Loose means an owned copy with neither a folder nor an active deck assignment. Moving a deck copy into a Binder folder preserves its deck entry as virtual, while deleting the deck releases the physical copy to Loose. The add-copy dialog offers Loose, existing Binder folders, and existing decks. Proxy/virtual deck entries do not allocate physical copies. The binder icon shows owned-copy count and opens a touch-, hover- and keyboard-accessible popover; clicking pins it open until it is closed, Escape is pressed, or the user clicks outside. The copy dialog and popover use an overlay-matched style, with scrollable content for long forms and histories. Adding, editing, disposing, restoring and deleting copies patch the TanStack Query cache. D-034 disposal/deletion atomically converts the associated deck entry to virtual and invalidates deck-card data.
- `BinderPage.tsx` provides URL-backed `?view=all|binders` and `?binder=<id>` views; it defaults to the binder list, while selecting a binder opens its cards. It also provides a history filter for retained sold/lost/given-away copies, local filters, bulk and per-copy moves, and binder CRUD. Binder and Loose covers are card-shaped colored buttons (`BinderCover`) with the vector app logo (`/logo.svg`); a binder's color is `binders.color`, chosen from the twelve-color palette in `binderColors.ts` (D-056 and its amendment, D-057), and Loose has a fixed color. "Create binder" and "Modify" (name and color) open the same `BinderFormDialog`. Card lists in the binder views still reuse `CardTile` from the card browser, and deck covers are unchanged.
- `CardDetailsOverlay.tsx` loads card rulings and printings through cached queries. Non-English printings (D-074) show their printed name, type line and text where Scryfall has them, with a "Show English text" toggle; the printings list has a "Show printings in other languages" checkbox that adds `include_multilingual=true` to `prints_search_uri` (checked from the start when the opened card is not English), and names the language of each foreign printing. In the card-content panel it shows mana cost beside power/toughness, loyalty or defense, then WUBRG color circles and a rarity pill; the rows appear between the type line and oracle text for each rendered face. Print entries show current Scryfall EUR / foil EUR prices and reuse `CardTile` for flip, favorites, binder and deck actions.
- `src/features/decks/` provides user-scoped deck queries/mutations, the shared card-action popover, and `/v2/decks`. The page uses URL-backed `?view=all|decks` and `?deck=<id>`; it defaults to the deck list, while selecting a deck opens its cards. It hydrates printings through the shared collection service and reuses `CardFilters` and `CardTile`. Deck covers use rarity/type/date ranking; each shows its name and a rounded entry-count pill. The All cards view shows every entry (including the same printing in different decks) with a kind pill below each card; Binder entries identify the linked physical copy. Proxy entries have a thin dashed accent outline and matching subtly tinted pill; virtual entries are muted and visibly labeled. Deck deletion removes its entries via the existing database cascade and releases physical Binder copies to Loose. D-037 browser checks on 4 Nov 2026 confirmed the authenticated Niv-Mizzet Reborn Binder copy in Farde noire was added to `test`, its entry persisted after reload, and the deck icon showed one entry. - Supabase user-owned tables use the reusable `useRealtimeInvalidation` hook; Realtime payloads invalidate and refetch under RLS, while local mutation echoes are ignored after cache patching. Binder copy and deck mutations (`useBinderCopies`, `useDeckManagement`, except `createDeck`) are optimistic (D-071): `onMutate` patches the copies and deck-entry caches the way the database functions and triggers will (helpers in `src/features/optimisticCache.ts`: `patchLists`/`restoreLists` snapshots, `releaseDeckEntriesOf` for entries that turn virtual, `toOptimisticCopy`/`toOptimisticDeckEntry`; new rows use an id chosen by the caller, server-created deck entries a temporary `optimistic-…` id), `onError` restores, `onSuccess` swaps in the server row, and `onSettled` refetches the linked list without awaiting it. Cross-device UI behavior has not been separately tested.
- `src/features/scan/` holds the card scanner (D-061). `ScanPage` reads `?mode=` with a nuqs string-literal parser (pushes history, so Back returns to the mode choice). `useCamera` opens the rear camera (`facingMode: environment`, ideal 3840×2160) while the view is mounted, stops its tracks on unmount, and returns a `starting | live | error` state with a reason (insecure, unsupported, denied, not-found, in-use, unknown) and `retry`. `ScanCamera` shows the video (`playsInline muted`, `object-fit: cover` in a 4:3 landscape box) or the error message, draws `GuideFrame` over it and gives the instruction as `aria-live` text. Guide (D-065, replacing D-061's card outline): one centered 4:1 box, 90% of the view width, that the user fills with the info line held close (the iPhone then switches to macro), plus a small card sketch showing which part goes in the box; `guideFrame.ts` holds `VIEW_RATIO`, `GUIDE_BOX_RATIO`, `GUIDE_RECT` (fractions, reused by the OCR), `INFO_LINE_WIDTH_MM` and `GuideStatus` (`aiming | aiming-title | reading-collector | reading-title | found`; the `-title` states are the name fallback in the same box, D-065 step 2, and the card sketch then marks the name). Recognition prototype (D-062), stages 1 and 2: `frameGeometry.ts` maps the guide box to video pixels through the `object-fit: cover` crop (`getGuideRect`, pure, tested; 1944×486 px for a portrait 4K video); `useSteadyFrame` samples a 96×24 gray copy of the box every 250 ms and, after 3 samples with an average change below 20 (re-armed above 30, values tuned on a phone), cuts the box out of the full-resolution frame as the `collector` strip; a steady card shows `reading-collector`. `useStripReading` cleans the box strip (`prepareStrip.ts`: enlarge, Otsu black and white, invert white-on-black text, white margin) and reads it through `ocr.ts` as the current target: `collector` is cut into its two rows (`splitStripRows` in `prepareStrip.ts`, at the emptiest middle row), each read as one line with its own characters (`NUMBER_ROW_CHARACTERS` without S, so a 5 can't come out as S; `SET_ROW_CHARACTERS`), falling back to reading the whole strip as one block when that gives nothing, and parsed with `parseCollectorLine.ts` into `{ setCode, collectorNumber }` (O, I/L and S misread in the number become 0, 1 and 5; a padded number of 3+ digits wins over a shorter number token on the same line); `title` (name fallback) is matched line by line with `matchCardName.ts` against the cached Scryfall `cardNames` catalog (letters only, approximate substring match, one error per five letters, front faces of double-faced cards indexed; pure, tested). `ScanCamera` switches to `title` after 2 captures in a row whose set and number failed, or with a "Read the name instead" button, and back after a found card or with "Read the set and number instead". `ocr.ts` is the only file that touches tesseract.js: it loads it with a dynamic `import()` (own chunk), starts one English worker while the camera is live, and fetches the engine and language data from the jsDelivr CDN (library default, cached in IndexedDB); its `opencollective-postinstall` script is left blocked on purpose. `usePrintingLookup` looks the parsed set and number up with Scryfall's `/cards/:code/:number`, or a matched name with `/cards/named?exact=` (the default printing; `onFound` passes `{ byName: true }` and Add mode then opens the printing list at once), through `createApiClient` (TanStack Query, same key shape as `useScryfallCardsSearch`, 24 h `staleTime`, `retry: false` so a misread 404 costs one request); ## Data and state

- `src/features/card-browser/useScryfallCardsSearch.ts`: TanStack Query hook, key `["scryfallCards", route, params, seed]`, enabled only when a route is given, 24 h `staleTime`. It uses `src/services/createApiClient.ts`, which normalizes `card` responses to `[card]` and `list`/`catalog` responses to `data`, and throws on Scryfall errors.
- `src/hooks/useFetchUrl.ts`: fetches auxiliary Scryfall URLs, key `["fetchedUrl", purpose, url]`, validates HTTP status and that the response contains a `data` array, then returns that array. A missing URL returns an empty array. Both URL hooks accept a fixed stale time or a query-based stale-time function; the card-name catalog is stale at the next local 04:00 based on its `dataUpdatedAt`.
- `src/services/fetchScryfallCards.ts` performs a validated, abortable Scryfall collection request bounded to 75 identifiers; favorites use it to hydrate each paginated set while preserving database ordering and skipping cards no longer found by Scryfall.
- `src/services/fetchScryfallCardsForIds.ts` deduplicates IDs and hydrates them sequentially in batches of at most 75 with a short inter-request gap. `useScryfallCardsForIds` caches these batches for the Binder card lists and personal search.
- Binder schema migrations create `binders` and per-copy `binder_cards`; loose copies remain user-owned through `binder_cards.user_id`. Migration `20261107084804_exclusive_deck_copy_storage` enforces exclusive Binder/deck/Loose location, provides atomic copy-to-deck and location-change functions, and preserves pre-migration dual assignments in the private rollback table until rollback. Migration `20261115163138_binder_color` (D-056) adds `binders.color` (lowercase `#rrggbb`, default `#1f2a6b`, check constraint) and a column-level `update (color)` grant, because updates on `binders` are granted per column; it must be applied before an app version that reads or writes the color is deployed. Every migration has a matching manual rollback in `supabase/rollback/`, and exposed user data tables require least-privilege grants, RLS policies, and pgTAP coverage.
- `useRealtimeInvalidation` listens to user-filtered changes for favorites, binders and binder copies; notifications are invalidation signals, not trusted data.
- `PersistenceProvider.tsx` persists `fetchedUrl` queries except `cardNames`, plus `scryfallCards` queries whose second key is `"cards/search"`, in `localStorage`. The roughly 687 KB Scryfall card-name catalog is prefetched per app session (in idle time after the first screen, or at once by Search and Scan) but not persisted because the combined cache exceeds the 2-million-character safety threshold. Random and single-card queries are not persisted.
- `queryProvider.ts`: `gcTime` is 24 h and must stay >= the persisted data's max age.
- `QueryDevToolsProvider.tsx` loads Devtools lazily and only when `import.meta.env.DEV`.
- `src/app/devIndicator.ts` (+ `.css`) draws a striped amber/black frame around the window so the dev server is recognizable; `main.tsx` imports it only when `import.meta.env.DEV`, so neither file reaches the production build. It sits outside React with `pointer-events: none`. Its colors and z-index stay in its own CSS (stylelint allows hex colors in that one file) so nothing of it lands in the production CSS through `tokens.css`.
- `features/card-filters/` uses TanStack Table and `nuqs` to filter by color, rarity, type, place and card kind, sort by name/CMC/rarity/price/place, and keep filter state in the URL. Place and kind filters are enabled only for collection search; other pages keep their existing controls.
- Many files contain debug `console.log` calls (e.g. `createApiClient.ts`, `useFetchUrl.ts`). Do not add more; ask before removing. The card renderer's logs were removed in D-058.
- Prices are current per-printing Scryfall data, not history or collection valuation.

## Source layout

- `src/main.tsx`, `src/app/` — entry, providers, V2 layout, router and the route error page (`RouteErrorPage.tsx`).
- `src/features/scryfall-card-renderer/` — shared card renderer. `types.ts` defines its raw input (`RawScryfallCard`) and normalized output (`NormalizedCard`); `normalizeCard.ts` maps raw Scryfall cards to the internal shape. Each normalized face keeps the English `name`, `typeLine` and `oracleText` and adds `printedName`, `printedTypeLine` and `printedText` (null when Scryfall has none); `withTextLanguage` puts the printed ones in place for display, and `CardRenderer`'s `textLanguage` prop (`printed` by default, or `oracle`) picks which (D-074). `scryfallCardLayouts.ts` and `components/` (one/split/toggle/flip/meld faces, `OracleText`, `extras/` for saga, class, case, leveler, mutate, prototype) consume that shape. Each card of a meld trio shows the other two (a piece: its partner and the result; the result: both pieces), names first, then images from one `useScryfallCardsForIds` request; the renderer imports nothing from `card-browser`. Related cards open through the optional `onOpenCard(cardId)` prop, supplied by the page that owns the overlay (D-059). The V2 details overlay uses it.

- `src/features/binder/` — Binder copy data and mutations, copy metadata form/popover, binder-folder queries and the Binder page.
- `src/features/decks/` — user-scoped deck and deck-card queries/mutations, inline card action popover, and the Decks page.
- `src/features/cardLanguages.ts` — every language Scryfall prints cards in (D-074): Scryfall code, the name the app shows and stores in `binder_cards.language`, and the codes printed on the collector line. Used by advanced search, the Binder copy form (`LANGUAGES` in `binder/copyOptions.ts`), the scanner's Add mode and `languageNameOf`.
- `src/features/card-filters/` — V2 browser and favorites filtering, sorting, URL parsers and table setup.
- `src/features/scan/` — card scanner page, camera hook, guide box (D-061, D-065; see above).
- `src/features/navigation/` — V2 desktop/mobile navbar and theme toggle (see above).
- `src/hooks/`, `src/services/` — see Data and state.
- `src/styles/tokens.css` — design tokens, imported by `main.tsx`: the dark/light theme colors plus the shape (radii), motion (two durations), focus ring, global z-index layers and identity colors (mana, rarity) that are the same in both themes. `ThemeContext.ts` and `ThemeProvider.tsx` provide shared theme state and synchronize the document theme and browser theme color. `src/styles/base.css`, imported right after the tokens, holds the body text size, the one global `:focus-visible` ring and the reduced-motion rule; components override the ring only for a different offset. `src/styles/forms.css`, imported next, holds the shared form field classes (`.field`, `.field__input` and their `--soft` variants for the Binder forms and popovers); a form's own class overrides only what differs. `src/styles/layout.css`, imported after it, holds the page classes the Search, Favorites, Binder and Decks pages share (`.page`, `.page__heading|title|toolbar|message`, `.page__control`, `.page__button`, `.page__label`, `.page__card-actions|card-action`, `.page__cover-card`, `.card-grid`, `.pagination` and `.pagination__button`); a page's own CSS adjusts them by being more specific or by coming later. Style a page's own controls with these classes, never with a page-wide `button`/`select`/`input` rule: such a rule also restyles every component rendered inside the page (D-053 Phase 4a). It is deliberately not in a `@layer`, because unlayered component rules such as `.browser-card` would beat it. `src/styles/splash.css` (the splash screen and page reset) is linked from `index.html`. `src/app/App.css` holds layer styles.
- `src/assets/icons/` — individual inline SVG React components, with navigation icons grouped under `navigation/`. `public/` contains site-root branding SVGs and favicons.
- `docs/` — `architecture/` guides (overview, state/data flows, and source reference), theme/Scryfall notes, file conventions, external resources, and filter guidance. Some historical notes may lag the code; verify in source.

## TypeScript

## Versioning

The app uses Calendar Versioning (CalVer): `YYYY.M.MICRO`, unpadded (e.g. `2026.11.0`, then `2026.11.1`).

- `YYYY.M` is the month of the release (UTC). `MICRO` counts releases within that month, starting at `0`.
- Do not pad the month: write `2026.8.0`, not `2026.08.0`. npm expects a SemVer-style version, which forbids leading zeros.
- The version says *when* a release shipped, not whether it is compatible. Breaking changes are called out in the changelog instead (see below).
- Roadmap milestones (for example "full deck-building tools") are named in `README.md` or `DECISIONS.md`; they are not encoded in the version.

**Single source of truth:** `version` in `package.json`. `package-lock.json` must match. Change both only with `npm version`; never hand-edit. Do not write the version number in prose elsewhere, except the stamped lines listed below.

**Bump rules** for versioning:

| Situation | Command |
| --- | --- |
| Another release in the same month | `npm version patch` (increments `MICRO`) |
| First release of a new month | `npm version YYYY.M.0` (explicit, e.g. `npm version 2026.12.0`) |

- Bump only when releasing, never per commit. Refactors, docs and tests ship in the next release.
- The month in the version is the month of the release (merge to `main` and tag), not the month the work started.
- The `minor` and `major` keywords of `npm version` carry no meaning here; do not use them.

**Public contract** (what the `### Breaking` changelog heading protects):

- URL structure and query params (`/v2/search?q=`, `?card=`, `?view=`, `?binder=`, `?deck=`, filter params) and `/v2/auth/callback`.
- Supabase schema, grants and RLS policies (tables, columns and constraints that user data depends on).
- Persisted browser data (`localStorage` keys written by `PersistenceProvider`).

Component structure, CSS and Scryfall response handling are not part of it. Any change to the contract is listed under `### Breaking` in that release's `CHANGELOG.md` section and recorded in `DECISIONS.md`.

**Branches and deployment.**

| Branch | Role |
| --- | --- |
| `feature/<name>` | One change (usually one decision, e.g. `feature/d-073-hand-of-the-day`), branched from `dev` |
| `dev` | Integration branch. Every pull request targets `dev`, never `main` |
| `release/YYYY.M.MICRO` | Short-lived branch cut from `dev` to prepare and regression-test one release |
| `main` | Released code only; production is deployed from it (Netlify) and every merge into it carries a release tag `vYYYY.M.MICRO` |

- Open pull requests with `--base dev`. A pull request into `main` would also carry every unreleased `dev` commit. Pull requests are squash-merged into `dev` (title ends with `(#N)`).
- When `dev` moves on while a pull request is open and the two conflict, merge `dev` into the feature branch (no rebase, so no force-push), resolve, rerun the checks, and push.
- Nothing reaches `main` except through a release branch (or a hotfix branch, below) that passed the regression tests, and a release tag is created for every release.

**Release flow** (solo developer). An agent releases only when asked; a request to release covers every step below, including the push.

1. **Daily work:** feature branches (`feature/<name>`) are merged into `dev` through pull requests. `package.json` keeps the last released version; `CHANGELOG.md` collects nothing until release time.
2. **Regular release** from `dev`:
   1. `git switch -c release/YYYY.M.MICRO dev` (the version the release will get, per the bump table).
   2. Regression tests on the release branch, before anything is merged into `main`: `npm run typecheck`, `npm run lint`, `npm run lint:css`, the tests (`node --experimental-strip-types --test "tests/**/*.test.ts"`) and `npm run build` must pass; then serve the build (`npm run preview`) and smoke-test it in a browser: Home shows the hand of the day, a card opens its details, Search returns results, and the Login, Favorites, Binder, Decks and Scan pages load without console errors. A failure stops the release: fix it on `dev` (through a pull request) and cut the release branch again.
   3. Update `CHANGELOG.md`: a new `## [YYYY.M.MICRO] - YYYY-MM-DD` section under `## [Unreleased]`, written for users (`### Added`, `### Changed`, `### Fixed`, `### Breaking` when the public contract changes, and always `### Database`, saying which migration is needed or "No migration in this release."). Development-only tools are left out.
   4. Decisions: move each implemented decision from `DECISIONS.md` to the end of `DECISIONS_HISTORY.md` with `- Status: Implemented` and `- Release: vYYYY.M.MICRO`; replace every remaining `Release: pending (on dev)` there with the version.
   5. Update the version stamp in this file's header (check date and app version).
   6. Commit as `Changelog and decision releases for YYYY.M.MICRO`.
   7. `npm version patch -m "Release %s"` (or `npm version YYYY.M.0 -m "Release %s"` for a new month): it commits both package files and creates the annotated tag `vYYYY.M.MICRO`.
   8. `git switch main && git merge --no-ff release/YYYY.M.MICRO` (message `Merge branch 'release/YYYY.M.MICRO' into main`), then `git switch dev && git merge --no-ff main` (`Merge branch 'main' into dev`).
   9. `git push origin main dev --follow-tags`, then delete the release branch locally (`git branch -d`) and the feature branches merged in this release, locally and on `origin` (only branches whose work is in `dev`).
   10. Close the GitHub issues this release finishes: for each decision moved in step 2.4 that has an `- Issue: #N` line, close issue N with `gh issue close N --reason completed --comment "Released in vYYYY.M.MICRO (D-0xx)."`, but only once **every** decision linked to that issue is implemented and released (an issue split into several decisions stays open until the last one ships). Mention the closed issues in the release summary.
3. **Hotfix** (a fix that can't wait for `dev`):
   1. Branch from the latest release tag: `git switch -c YYYY.M.MICROa vYYYY.M.MICRO` (for example `2026.11.3a` from `v2026.11.3`). The letter only names the branch; it is not a version, because npm versions can't carry it.
   2. Fix and commit there, and test on the device concerned.
   3. Release it with steps 2.2 to 2.9 on the hotfix branch instead of a release branch: the release gets the next `MICRO` with `npm version patch` (for example `2026.11.4`), the hotfix branch is merged into `main`, then `main` into `dev`.
   4. Work tried on the hotfix but not kept stays on a side branch (for example `2026.11.3a-low-light`) and is not merged; the decision records why.
4. Pre-release builds, only if needed: `2026.12.0-beta.1`.

A release that depends on a Supabase migration needs that migration applied to the linked project before the app is deployed.

**Other files** concerned by versioning:

| File | Rule |
| --- | --- |
| `package.json`, `package-lock.json` | Tracked version; `npm version` only |
| `CHANGELOG.md` | Keep a Changelog format; `Unreleased` on top, one section per release; breaking contract changes under `### Breaking` |
| `DECISIONS.md`, `DECISIONS_HISTORY.md` | Not versioned; dated entries. Implemented or superseded decisions move to `DECISIONS_HISTORY.md`; an implemented one gets `- Release: pending (on dev)` until it ships, then `- Release: vYYYY.M.MICRO`. A decision that comes from a GitHub issue carries `- Issue: #N` under its date (several decisions may share one issue); the issue is closed in release step 2.10 |
| `AGENTS.md` | Not versioned; once the first version tag exists, the header stamps the check date and the app version |
| `README.md`, `docs/` | No hardcoded version; dated notes; link to the changelog |
| Supabase migrations | Timestamp-named by the CLI, never part of the app version; each has a matching rollback in `supabase/rollback/`; the changelog says which release needs which migration |
| `supabase` CLI devDependency | Keep pinned to an exact version; bump deliberately |
| Other dependencies | Caret ranges plus lockfile; no separate versioning rule |
| `/v2` and any future layout prefix | UI layout names, not app versions; see "UI layouts are not app versions" |
| `CLAUDE.md`, `.github/copilot-instructions.md` | Pointers to this file; no version |

### UI layouts are not app versions

Route prefixes such as `/v2` name a UI layout, not a release. Never read them as part of the app version.

| Layout | Status |
| --- | --- |
| `/v2` | Only layout; active default |
| `/v1` | Removed (no routes listed above) |

- Adding, deprecating or removing a layout is judged by one test: does something users relied on stop working? If yes, list it under `### Breaking`.
- Removing a layout prefix without a redirect is a breaking change.
- Do not rename `/v2` or drop its prefix without a decision; it is a contract change.
- If a second layout is ever introduced, run it in parallel under its own prefix, keep the data pipeline (hooks, `createApiClient`, `normalizeCard`) shared rather than forked, and record each status change (active, maintained, deprecated, removed) in `DECISIONS.md`.

## Conventions

- Always create a matching rollback SQL file alongside every forward Supabase migration, using the same migration filename with `_reverse` appended before `.sql` and placing it in `supabase/rollback/`. Keep rollback scripts out of `supabase/migrations/` so Supabase does not apply them as forward migrations.
- Keep the pipeline separated: raw Scryfall data enters through the hooks and client, `normalizeCard.ts` maps it, renderer components consume the normalized shape only.
- Use `createApiClient` for Scryfall card/list endpoints. Auxiliary URL hooks use direct `fetch`; keep their query-key conventions when extending.
- Be gentle with Scryfall: no request loops or bursts. Check Scryfall's API docs for current rate-limit and header requirements before adding new fetch patterns.
- Keep new UI aligned with the tokens in `src/styles/tokens.css` and the component-local CSS pattern: no hard-coded colors, global z-index values, corner radii or the shared durations (`src/styles/splash.css` is the exception). Do not add per-component focus rings or reduced-motion transition overrides; `base.css` handles both (a `prefers-reduced-motion` block is still needed to cancel a hover transform).
- Follow `docs/file-conventions.md` for naming and file types, including the CSS rules (BEM class names, class selectors only, tokens, breakpoints); run `npm run lint:css` after CSS changes.
- Do not convert unrelated files, rename folders, or "clean up" unused files without being asked.
